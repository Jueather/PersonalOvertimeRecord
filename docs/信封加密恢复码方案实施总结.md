# WebDAV 同步加密 · 信封加密与恢复码兜底方案实施总结

日期：2026-10-01
模块：`app`（Kotlin）
状态：已实施，全量单测通过，debug / release(R8) 构建成功

---

## 1. 背景与目标

旧方案直接用"同步密码"经 PBKDF2 派生密钥后 AES-GCM 加密云端备份：

- 密码是唯一解密钥匙；
- 密码一旦遗忘，云端数据**永久不可恢复**；
- 更换设备时若密码输入错误，同样无法取回历史数据。

本次与用户确认后实施：

- **方案一：本机生物识别查看/重置同步密码**；
- **方案二：信封加密 + 随机恢复码**（忘记密码时的离线找回通道）；
- 方案三（密码提示）未实施。

目标：在不降低日常加密强度的前提下，做到"密码丢了数据不丢"，并保证旧备份数据平滑兼容、下次同步自动升级。

---

## 2. 总体设计：信封加密（Envelope Encryption）

把"加密数据的密钥"与"用户记忆的秘密"解耦：

1. 生成一个随机 **256 位数据密钥 DEK**（Data Encryption Key），备份正文由 DEK 做 **AES-256-GCM** 加密；
2. DEK 不直接存储，而是被两份独立秘密各自**包裹（wrap）**一份：
   - **密码槽（pwdSlot）**：由同步密码包裹，供日常解密；
   - **恢复槽（recSlot）**：由随机恢复码包裹，供遗忘密码时兜底；
3. 任一把钥匙都能解开 DEK；用恢复码解开后可设置新密码重新包裹密码槽，**恢复槽原样保留，恢复码持续有效**。

```
                         ┌─ pwdSlot: KEK(密码) 包裹 DEK
备份明文 ──AES-GCM(DEK)──┼─ recSlot: KEK(恢复码) 包裹 DEK
                         └─ payloadIv + 密文正文(含 GCM tag)
```

KEK 派生与正文加密均复用 `EncryptionUtils` 的同一套底层原语（PBKDF2-HmacSHA256 600,000 次 + AES-GCM），保证加密强度与既有实现一致。

## 3. 数据格式

### 3.1 线路格式（WebDAV 上的字符串）

```
PORE_ENV1: + Base64(二进制信封, NO_WRAP)
```

通过固定前缀 `PORE_ENV1:` 与旧格式区分。

### 3.2 二进制信封布局（版本 1）

| 区段 | 长度 | 说明 |
|---|---|---|
| magic | 4 B | `"PEV1"` (0x50 0x45 0x56 0x31) |
| version | 1 B | 固定为 1 |
| pwdSlot | 76 B | 密码包裹槽 |
| recSlot | 76 B | 恢复码包裹槽 |
| payloadIv | 12 B | 正文 GCM IV |
| payload | 变长 | 正文密文（含 16 B GCM tag） |

每个包裹槽 76 字节，定长拼接：

| 槽内字段 | 长度 |
|---|---|
| salt | 16 B |
| iv | 12 B |
| wrappedDek | 48 B（32 B DEK + 16 B GCM tag） |

每份包裹使用各自独立的随机 salt/iv；GCM 认证保证密码错误或数据篡改时直接失败，不会得到错误明文。

---

## 4. 恢复码（Recovery Code）

- 10 个随机字节 = **80 位熵**，经 **Crockford Base32** 编码为 16 个字符；
- 展示形式 4 组 × 4 位，例：`7K2M-9XQF-4BT8-N6VD`；
- 字母表 `0123456789ABCDEFGHJKMNPQRSTVWXYZ` 剔除了易混字符（无 I/L/O/U）；
- 输入规范化（`normalize`）容错：去连字符/空格、转大写、`O→0`、`I/L→1`，降低手抄录入失败率；
- 80 位熵 + 恢复码只以 GCM 包裹形式存在云端（无法离线批量验证），足以抵抗猜测。

---

## 5. 密钥生命周期与本地存储

密钥材料保存在 `SettingsManager` 中，底层为 **EncryptedSharedPreferences**（不落明文到普通配置）：

| 存储键 | 内容 |
|---|---|
| `sync_dek` | 本机 DEK（Base64） |
| `sync_recovery_code` | 恢复码明文（仅发起设备/已找回设备保存） |
| `sync_recovery_slot` | 恢复槽字节（Base64 的独立 76 B 槽） |
| `sync_recovery_pending` | 是否已生成恢复码但用户尚未确认保存（红色提醒） |

关键规则：

- **发起加密的设备**：同时持有 DEK 与恢复码明文；
- **新设备用密码接入**：只落盘 DEK + 恢复槽，**不知道恢复码明文**，但上传时恢复槽原样透传，恢复码仍有效（用户也可在设置页重新签发恢复码）；
- **换密码**：仅重新包裹 pwdSlot，recSlot 字节透传；
- **用恢复码找回**：解开 DEK 与恢复槽 → 用新密码重包密码槽 → 写回本地材料，恢复码继续沿用。

## 6. 同步链路与旧格式迁移

`SyncManager` 下载后统一经 `resolveCloud()` 解析三种云端形态：

1. **信封格式**（`PORE_ENV1:` 前缀）：按密码槽解密；密码正确且本机无材料时，自动为新设备落盘 DEK + 恢复槽；
2. **旧版裸密文**（无信封 magic 的 Base64 密文）：用 `EncryptionUtils` 旧逻辑解密（含 "G2" 600k 与历史 "GM" 65,536 次两种格式）；
3. **明文 JSON**（内容以 `{`/`[` 开头）：直接读取。

上传经 `buildUploadWire()` 统一输出信封格式，DEK 获取优先级：

```
本地密钥材料 → 云端信封中解出的 DEK → 新生成 DEK（同时生成恢复码，置 recovery pending）
```

因此**旧备份在下次成功同步时自动升级为信封格式，用户无感迁移**。

`WebDAVManager` 拆分为：

- `uploadRawFile()` / `downloadRawFile()`：纯传输，不做加解密；
- 旧 `uploadFile()` / `downloadFile()`：保留为薄包装（兼容无其他调用方）。

新增公开入口 `SyncManager.validateAndApplyRecovery(recoveryCode, newPassword)`：下载云端 → 用恢复槽校验恢复码 → 保存新密码与 DEK 材料（不持同步锁，供找回流程调用）。

## 7. 用户界面与交互

### 7.1 设置页（`activity_settings.xml` / `SettingsActivity.kt`）

同步加密区域新增：

- **待保存提醒**（`tvRecoveryPending`，红底）：恢复码已生成但未确认离线保存时持续提示；
- **查看同步密码**：生物识别（指纹/面容）通过后展示；
- **查看恢复码**：生物识别通过后展示，可复制、可重新签发；
- **用恢复码找回**：忘记密码时输入恢复码 + 设置新密码完成找回。

关键行为：

- 开启加密保存设置后，自动生成 DEK 与恢复码并弹出**不可取消**对话框，引导用户立即离线保存；
- 生物识别统一走 `BiometricManager.showAuthenticationPrompt()`，失败/取消无敏感信息泄露。

### 7.2 同步结果提示

- 前台同步成功且本次生成了恢复码（`SyncReport.recoveryCodeGenerated`）：弹窗引导前往设置页；
- 后台自动同步完成迁移：`AutoSyncManager` 发高优先级通知"请保存同步恢复码"，点击直达设置页；
- 密码不匹配（`ENCRYPTION_MISMATCH`）的提示文案统一改为引导"检查密码或用恢复码找回"。

## 9. 安全性质小结

- **前向安全强度**：正文 AES-256-GCM，KEK 经 PBKDF2 600,000 次派生，与主加密口径一致；
- **防篡改/防错误解密**：包裹槽与正文均带 GCM tag，错误秘密或数据损坏直接失败；
- **最小暴露**：新设备不持有恢复码明文；本地材料存于 EncryptedSharedPreferences；查看需生物识别；
- **备份文件合规**：延续项目约定，备份内容不含密码字段；
- **恢复码抗猜测**：80 位熵，且云端只有包裹形态，无法离线批量枚举。

## 11. 已知边界与后续建议

- 恢复码是**最后兜底通道**，用户需离线妥善保存；泄露恢复码等同于泄露其中一把钥匙，可通过"重新签发恢复码"使旧码失效（重包恢复槽）；
- 建议在真机走一遍端到端验收：开启加密 → 记录恢复码 → 卸载重装/换新设备 → 分别用密码与恢复码恢复；
- 未实施方案三（密码提示），如后续需要可在信封之外作为独立辅助手段补充。

> 补充修复（2026-10-01）：初版在"重装后开启加密"时会不看云端直接生成新 DEK，
> 首次同步覆盖云端信封导致**原恢复码失效**。现修复为：
> `SyncManager.bootstrapKeyMaterialOnEnable()` 先探测云端——已是信封则接入原 DEK/恢复槽
